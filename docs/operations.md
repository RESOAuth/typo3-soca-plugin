# Operations, recovery and privacy

Only TYPO3 frontend users on one configured site, with backend users excluded are protected. API grants, delegated access, application passwords, WebDAV/mobile flows, machine accounts and back-channel logout are outside this initial profile. Native password, reset, permission and session APIs remain authoritative. There is no automatic redirect from the local login page, so an unavailable provider cannot trap an administrator in a redirect loop.

Before rollout, keep a dedicated local administrator with strong local authentication and native MFA where supported. Test its password login in a separate browser. SOCA never admits protected host administrators, and the native password form stays available.

For recovery, set `SOCA_EMERGENCY_DISABLE=1`, restart PHP workers and run `vendor/bin/typo3 soca:manage invalidate`. New callbacks and tests fail closed; the replay ledger is emptied when the emergency gate runs. SOCA session markers are removed and native sessions are logged out on the next covered request. Local administrator sessions without a SOCA marker are preserved. Re-enable only after the cause is resolved and candidate evidence is valid for the effective revision. Test this before rollout and after upgrades.

For an ordinary maintenance disable, set `enabled: false` and run `invalidate` before re-enabling. The explicit invalidation is necessary even when no request observes the disabled interval. Before disabling or uninstalling the native extension, invalidate pending transactions and revoke affected native user sessions. Once the extension is unloaded, its session checks no longer run and existing sessions follow host expiry. Matomo's deactivate hook also purges the ledger. Native app-disable notifications, cross-worker administrative session deletion and all rolling-upgrade/restore cases are not yet comprehensively tested.

The plugin checks its SOCA session revision, lifetime and native account/group/site eligibility on covered host requests. The default absolute SSO lifetime is 900 seconds, with a 60–86400 second range. Unlinked identities cannot log in again; existing sessions are bounded by their remaining absolute lifetime. Policy/configuration changes and disabled/ineligible users are rejected on the next covered request. Nextcloud bootstrap applies to loaded browser application requests; server endpoints that do not boot apps need separate verification. Provider session revocation without a local policy/account change cannot propagate until local expiry because back-channel logout is not implemented.

Private keys and state keys remain in deployment-managed files outside application data. Ephemeral PKCE, nonce and discovery snapshots are AES-256-GCM encrypted in native host session storage, using the separate state key and browser-associated data. The database replay ledger holds only hashes, revision and expiry. State expires after 300 seconds and is deleted atomically before token exchange. Expired ledger rows are removed at new login attempts; Nextcloud also schedules a 300-second cleanup job. Expired sealed session entries are cleaned on the next login attempt and on native session expiry, so physical deletion follows host session retention rather than a separate sweeper.

No external access, refresh or ID token is intentionally retained after the callback. Browser storage APIs and extra plugin cookies are unused. Public metadata and JWKS contain no identity policy, claims or private key material. Native host session authentication tokens are host-owned and follow its retention rules. Routine rejection logs contain redacted references, without tokens, callback parameters or claim dumps. The demo Apache access log omits query strings. Configure equivalent redaction at every proxy, CDN and production web server.

The optional public Dynamic CIMD service receives only public metadata encoded in the URL. OIDC discovery, JWKS, token and optional UserInfo requests go to the explicitly configured issuer's advertised endpoints over validated HTTPS. The network transport rejects private/reserved DNS answers, mixed public/private resolutions, redirects and oversized responses. Restricted egress should permit only the trusted issuer endpoints, document host and configured proxy. Transport limits apply after DNS resolution; resolver total deadlines and hostile-network fault testing remain gaps.

Back up the native database, deployment JSON, stable signing key and state key together with an encrypted, access-controlled backup policy. Restore can revive links or pending ledgers unless the operator immediately invalidates transactions and rechecks current revocations. Lost signing keys require a new candidate profile and potentially a new proxy client ID/pairwise subject; never infer a replacement subject from email. Backup/restore and lost-key drills are required before production acceptance.

Uninstall does not delete local users, passwords, permissions or identity links. Keep those records through reversible disable/reinstall. Permanent deletion is a deliberate deployment operation: disable, invalidate, revoke relevant native sessions, export the audit reference, delete only SOCA tables/app evidence, remove secret files and account for encrypted backups. There is no unauthenticated destructive endpoint or automatic account deletion.

Availability, failover and load objectives have not been validated. Fail closed when provider/documents/keys are unavailable or invalid, and use local recovery. Proposed production acceptance targets are less than 3 seconds p95 for a complete healthy callback (excluding human interaction), zero unexpected account duplication and recovery within 30 minutes with a known-good backup. Treat these as untested objectives, not measured promises.
